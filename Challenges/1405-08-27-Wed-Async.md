## سؤال 1
قطعه کد زیر را در نظر بگیرید. با توجه به نحوه اجرای متدهای Asynchronous و زمان تکمیل Task، ترتیب قطعی خروجی برنامه چیست؟

```csharp
var tcs = new TaskCompletionSource<bool>(
    TaskCreationOptions.RunContinuationsAsynchronously);

async Task ExecuteAsync()
{
    Console.Write("A ");
    await tcs.Task;
    Console.Write("B ");
}

var task = ExecuteAsync();

Console.Write("C ");

tcs.SetResult(true);

await task;

Console.Write("D ");
```
1. `A B C D`

2. `A C B D`

3. `C A B D`

4. ترتیب خروجی به ThreadPool وابسته است و قابل پیش‌بینی نیست.

- **گزینه صحیح:** **۲**

- **تحلیل عملکرد:** متد `ExecuteAsync` هنگام فراخوانی، اجرای خود را به‌صورت Synchronous روی Thread فراخواننده آغاز می‌کند. بنابراین ابتدا A چاپ می‌شود. سپس متد به `await tcs.Task` می‌رسد و چون Task هنوز تکمیل نشده است، اجرای متد معلق می‌شود و کنترل به فراخواننده بازمی‌گردد. در نتیجه C چاپ خواهد شد.

با اجرای `tcs.SetResult(true)`، Task تکمیل شده و Continuation مربوط به متد برای اجرا آماده می‌شود؛ بنابراین B چاپ خواهد شد. دستور `await task` نیز تضمین می‌کند که D تنها پس از پایان کامل متد چاپ شود.

- **نکته کلیدی مرور:** Asynchronous بودن به معنای نامشخص بودن ترتیب تمام دستورات نیست. وابستگی میان Taskها و استفاده از await می‌تواند ترتیب اجرای عملیات را تضمین کند.

## سؤال 2
قطعه کد زیر را در نظر بگیرید. با توجه به وضعیت Task هنگام اجرای await، کدام گزینه خروجی برنامه و دلیل ترتیب اجرای دستورات را به‌درستی بیان می‌کند؟

```csharp
async Task<int> CalculateAsync()
{
    Console.Write("A ");

    int result = await Task.FromResult(20);

    Console.Write("B ");

    return result * 2;
}

Console.Write("C ");

Task<int> task = CalculateAsync();

Console.Write("D ");

Console.Write(await task);
```
1. `C A D B 40`؛ زیرا هر await کنترل را به فراخواننده بازمی‌گرداند.

2. `C D A B 40`؛ زیرا متد async روی ThreadPool اجرا می‌شود.

3. `C A B D 40`؛ زیرا Task تکمیل‌شده باعث تعلیق متد نمی‌شود.

4. `C A B D 40`؛ زیرا Task.FromResult یک Thread جدید ایجاد می‌کند.

- **گزینه صحیح:** **۳**

- **تحلیل عملکرد:** ابتدا C چاپ می‌شود. سپس متد `CalculateAsync` فراخوانی شده و A را چاپ می‌کند. متد `Task.FromResult(20)` یک Task از قبل تکمیل‌شده برمی‌گرداند؛ بنابراین await نیازی به معلق کردن متد یا بازگرداندن کنترل به فراخواننده ندارد.

در نتیجه B چاپ شده، مقدار ۴۰ محاسبه می‌شود و یک Task تکمیل‌شده به فراخواننده بازمی‌گردد. سپس D چاپ می‌شود و await نهایی نیز بدون تعلیق مقدار ۴۰ را دریافت می‌کند.

- **نکته کلیدی مرور:** هر await الزاماً باعث Suspend شدن متد نمی‌شود. اگر Awaitable هنگام بررسی تکمیل شده باشد، متد می‌تواند بدون تعلیق به اجرای خود ادامه دهد.

## سؤال 3
در یک ASP.NET Core Application، دو متد زیر برای دریافت اطلاعات از یک سرویس خارجی نوشته شده‌اند. فرض کنید ۵۰۰ درخواست هم‌زمان وارد برنامه شوند و پاسخ سرویس خارجی به‌کندی دریافت شود. کدام تحلیل درباره Scalability این دو نسخه صحیح است؟

```csharp
// Version A
async Task<string> GetDataAAsync()
{
    return await Task.Run(() =>
        httpClient.GetStringAsync(url)
                  .GetAwaiter()
                  .GetResult());
}

// Version B
async Task<string> GetDataBAsync()
{
    return await httpClient.GetStringAsync(url);
}
```
1. نسخه A بهتر است؛ زیرا هر درخواست روی Thread مستقلی اجرا می‌شود.

2. هر دو نسخه یکسان‌اند؛ زیرا نوع بازگشتی هر دو Task است.

3. نسخه B ضعیف‌تر است؛ زیرا await باعث Block شدن Request Thread می‌شود.

4. نسخه B بهتر است؛ زیرا هنگام انتظار I/O یک ThreadPool Thread را Block نمی‌کند.

- **گزینه صحیح:** **۴**

- **تحلیل عملکرد:** در نسخه A، عملیات دریافت اطلاعات با استفاده از `Task.Run` روی ThreadPool زمان‌بندی می‌شود. اما فراخوانی `GetAwaiter().GetResult()` باعث می‌شود Thread اجراکننده تا تکمیل عملیات HTTP مسدود بماند.

با ورود تعداد زیادی Request هم‌زمان، تعداد زیادی ThreadPool Thread صرف انتظار برای پاسخ سرویس خارجی می‌شوند. در نتیجه ممکن است Threadهای کافی برای پردازش درخواست‌های جدید و اجرای Continuationها در دسترس نباشند.

در نسخه B، عملیات HTTP مستقیماً با await فراخوانی می‌شود. اگر Task هنوز تکمیل نشده باشد، متد معلق می‌شود و نیازی نیست یک Thread به‌صورت اختصاصی در طول زمان انتظار I/O اشغال شود. این تفاوت در بار Concurrent بالا تأثیر مهمی بر Scalability دارد.

- **نکته کلیدی مرور:** قرار دادن یک عملیات Blocking داخل Task.Run، آن را به Async I/O واقعی تبدیل نمی‌کند؛ بلکه محل Blocking را به ThreadPool منتقل می‌کند.

## سؤال 4
قطعه کد زیر را در نظر بگیرید. با توجه به اینکه متد `CalculateAsync` با کلمه کلیدی async تعریف شده است، هنگام فراخوانی آن چه اتفاقی می‌افتد؟

```csharp
async Task<long> CalculateAsync()
{
    long sum = 0;

    for (int i = 0; i < 100_000_000; i++)
    {
        sum += i;
    }

    return sum;
}

Console.WriteLine("Start");

Task<long> task = CalculateAsync();

Console.WriteLine("Middle");

Console.WriteLine(await task);
```
1. حلقه کامل اجرا می‌شود و سپس کنترل به فراخواننده بازمی‌گردد.

2. حلقه روی یک Thread جدید اجرا می‌شود و Middle بلافاصله چاپ می‌شود.

3. کامپایلر به دلیل نبود await از کامپایل برنامه جلوگیری می‌کند.

4. متد در هر تکرار حلقه Thread جاری را آزاد می‌کند.

- **گزینه صحیح:** **۱**

- **تحلیل عملکرد:** متد `CalculateAsync` با کلمه کلیدی async تعریف شده است، اما هیچ await در بدنه آن وجود ندارد. بنابراین تمام محاسبات حلقه به‌صورت Synchronous و روی همان Thread فراخواننده انجام می‌شوند.

هنگام فراخوانی متد، اجرای برنامه تا پایان حلقه درون متد باقی می‌ماند. پس از اتمام محاسبات، یک Task تکمیل‌شده حاوی نتیجه به فراخواننده بازگردانده می‌شود. در نتیجه دستور چاپ Middle تنها پس از پایان تمام محاسبات اجرا خواهد شد.

کامپایلر هشدار `CS1998` صادر می‌کند که نشان می‌دهد متد async فاقد await است و به‌صورت Synchronous اجرا خواهد شد. با این حال، در تنظیمات معمول این هشدار مانع کامپایل برنامه نمی‌شود.

- **نکته کلیدی مرور:** کلمه کلیدی async به‌تنهایی باعث ایجاد Thread جدید، اجرای موازی، آزاد شدن Thread یا افزایش Performance نمی‌شود.

## سؤال 5
در قطعه کد زیر، سه Task با وضعیت‌های متفاوت ایجاد شده‌اند. با توجه به تفاوت میان تکمیل شدن و موفقیت یک Task، خروجی برنامه چیست؟

```csharp
Task<int> first = Task.FromResult(10);

Task<int> second = Task.FromException<int>(
    new InvalidOperationException());

Task<int> third = Task.FromCanceled<int>(
    new CancellationToken(true));

var tasks = new[] { first, second, third };

Console.WriteLine(tasks.Count(t => t.IsCompleted));

Console.WriteLine(
    tasks.Count(t => t.Status ==
        TaskStatus.RanToCompletion));
```
1. ابتدا 1 و سپس 1

2. ابتدا 3 و سپس 3

3. ابتدا 3 و سپس 1

4. هنگام بررسی IsCompleted یک Exception رخ می‌دهد.

- **گزینه صحیح:** **۳**

- **تحلیل عملکرد:** در این مثال سه Task ایجاد شده‌اند که هر سه در وضعیت نهایی قرار دارند، اما نتیجه اجرای آن‌ها متفاوت است.

Task اول با `Task.FromResult` ایجاد شده و وضعیت آن `RanToCompletion` است. Task دوم با `Task.FromException` ایجاد شده و وضعیت آن `Faulted` است. Task سوم نیز با `Task.FromCanceled` ایجاد شده و وضعیت آن `Canceled` است.

خصوصیت `IsCompleted` برای هر سه وضعیت نهایی مقدار True برمی‌گرداند؛ بنابراین شمارش اول برابر ۳ خواهد بود. اما در شمارش دوم فقط Taskهایی انتخاب می‌شوند که وضعیت `RanToCompletion` دارند. از آنجا که تنها Task اول موفق بوده است، خروجی دوم برابر ۱ خواهد بود.

- **نکته کلیدی مرور:** Completion با Successful Completion یکسان نیست. برای بررسی موفقیت یک Task می‌توان از `IsCompletedSuccessfully` یا وضعیت `RanToCompletion` استفاده کرد.

## سؤال 6
در قطعه کد زیر، یک Task ناموفق با دو روش متفاوت مورد استفاده قرار گرفته است. با توجه به نحوه انتشار Exception در await و Result، خروجی دو بلوک catch به‌ترتیب چیست؟

```csharp
Task<int> task = Task.FromException<int>(
    new InvalidOperationException("Failed"));

try
{
    int result = task.Result;
}
catch (Exception ex)
{
    Console.WriteLine(ex.GetType().Name);
}

try
{
    int result = await task;
}
catch (Exception ex)
{
    Console.WriteLine(ex.GetType().Name);
}
```
1. `InvalidOperationException` سپس `InvalidOperationException`

2. `AggregateException` سپس `AggregateException`

3. `InvalidOperationException` سپس `AggregateException`

4. `AggregateException` سپس `InvalidOperationException`

- **گزینه صحیح:** **۴**

- **تحلیل عملکرد:** در این مثال، Task با استفاده از `Task.FromException<int>` ایجاد شده و از همان ابتدا در وضعیت Faulted قرار دارد.

هنگامی که از `task.Result` استفاده می‌شود، Exception مربوط به Task در قالب یک `AggregateException` منتشر می‌شود. بنابراین اولین بلوک catch نوع Exception را AggregateException تشخیص می‌دهد.

اما هنگامی که از `await task` استفاده می‌شود، Exception اصلی Task مستقیماً منتشر می‌شود. در این مثال Exception اصلی از نوع `InvalidOperationException` است؛ بنابراین دومین بلوک catch همین نوع را چاپ می‌کند.

توجه داشته باشید که چون Task در این مثال از قبل تکمیل شده است، استفاده از Result باعث انتظار برای تکمیل Task نمی‌شود. تفاوت مورد بررسی در این سوال، نحوه انتشار Exception است.

- **نکته کلیدی مرور:** استفاده از await علاوه بر جلوگیری از Blocking غیرضروری، مدیریت Exceptionها را در مسیرهای Asynchronous ساده‌تر می‌کند.

## سؤال 7
قطعه کد زیر را در نظر بگیرید. سه متد Asynchronous فراخوانی شده‌اند و همگی منتظر تکمیل یک Task مشترک هستند. پیش از اجرای دستور `gate.SetResult(true)` چه خروجی‌ای مشاهده می‌شود؟

```csharp
var gate = new TaskCompletionSource<bool>(
    TaskCreationOptions.RunContinuationsAsynchronously);

int started = 0;

async Task WorkAsync()
{
    Interlocked.Increment(ref started);

    await gate.Task;
}

Task t1 = WorkAsync();
Task t2 = WorkAsync();
Task t3 = WorkAsync();

Task all = Task.WhenAll(t1, t2, t3);

Console.WriteLine(started);
Console.WriteLine(all.IsCompleted);

gate.SetResult(true);

await all;
```
1. `1` و `False`؛ زیرا Taskها به‌ترتیب اجرا می‌شوند.

2. `3` و `False`؛ زیرا هر سه متد آغاز شده‌اند اما هنوز تکمیل نشده‌اند.

3. `3` و `True`؛ زیرا هر سه متد Task خود را بازگردانده‌اند.

4. `0` و `False`؛ زیرا Task.WhenAll هنوز Taskها را اجرا نکرده است.

- **گزینه صحیح:** **۲**

- **تحلیل عملکرد:** هر بار که متد `WorkAsync` فراخوانی می‌شود، ابتدا شمارنده started با استفاده از `Interlocked.Increment` افزایش پیدا می‌کند. سپس متد به `await gate.Task` می‌رسد.

از آنجا که Task مربوط به gate هنوز تکمیل نشده است، متد معلق می‌شود و کنترل به فراخواننده بازمی‌گردد. این رفتار برای هر سه فراخوانی اتفاق می‌افتد. بنابراین پیش از رسیدن به `Task.WhenAll`، هر سه متد آغاز شده‌اند و مقدار started برابر ۳ است.

متد `Task.WhenAll` یک Task تجمیعی ایجاد می‌کند که تنها پس از رسیدن تمام Taskهای ورودی به وضعیت نهایی تکمیل می‌شود. چون gate هنوز آزاد نشده است، مقدار `all.IsCompleted` برابر False خواهد بود.

پس از اجرای `gate.SetResult(true)`، هر سه متد می‌توانند ادامه پیدا کنند و به پایان برسند.

- **نکته کلیدی مرور:** Concurrency الزاماً به معنی اجرای هم‌زمان روی چند Thread نیست. همچنین Task.WhenAll عملیات را آغاز نمی‌کند؛ بلکه تکمیل Taskهای ورودی را دنبال می‌کند.

## سؤال 8
در قطعه کد زیر، یک Async Delegate به متد `Task.Run` ارسال شده است. با توجه به نوع Task بازگشتی و نحوه تکمیل عملیات داخلی، کدام تحلیل درباره خروجی برنامه صحیح است؟

```csharp
var gate = new TaskCompletionSource<int>(
    TaskCreationOptions.RunContinuationsAsynchronously);

Task<int> task = Task.Run(async () =>
{
    int number = await gate.Task;

    return number * 2;
});

Console.WriteLine(task.IsCompleted);

gate.SetResult(21);

Console.WriteLine(await task);
```
1. خروجی False و 42 است؛ Task.Run تکمیل عملیات async داخلی را دنبال می‌کند.

2. خروجی True و 42 است؛ Task.Run فقط اجرای اولیه Delegate را دنبال می‌کند.

3. کد کامپایل نمی‌شود؛ زیرا نوع بازگشتی Task> است.

4. Task.Run تا تکمیل gate.Task یک ThreadPool Thread را Block می‌کند.

- **گزینه صحیح:** **۱**

- **تحلیل عملکرد:** در این مثال یک Async Delegate به `Task.Run` داده شده است. این Delegate ابتدا منتظر تکمیل `gate.Task` می‌ماند و سپس مقدار دریافت‌شده را در عدد ۲ ضرب می‌کند.

متد `Task.Run` دارای Overload مخصوص Delegateهایی است که یک Task برمی‌گردانند. در نتیجه Task بازگشتی فقط زمان‌بندی یا اجرای بخش اولیه Delegate را دنبال نمی‌کند، بلکه تکمیل عملیات Asynchronous داخلی را نیز دنبال خواهد کرد.

به این رفتار Unwrapping گفته می‌شود. بنابراین نوع Task بازگشتی `Task<int>` است، نه `Task<Task<int>>`.

پیش از اجرای `gate.SetResult(21)`، عملیات داخلی نمی‌تواند تکمیل شود؛ بنابراین مقدار `task.IsCompleted` برابر False خواهد بود. پس از تکمیل gate، مقدار ۲۱ در عدد ۲ ضرب شده و نتیجه نهایی ۴۲ به دست می‌آید.

- **نکته کلیدی مرور:** Task.Run هنگام دریافت Async Delegate، تکمیل Task داخلی را نیز دنبال می‌کند. اگر await داخلی تکمیل نشده باشد، Thread اجراکننده مجبور نیست در طول انتظار مسدود بماند.

## سؤال 9
در یک ASP.NET Core Application، Endpoint زیر برای دریافت اطلاعات از یک سرویس خارجی پیاده‌سازی شده است. هنگام Load Test با تعداد زیادی درخواست هم‌زمان، CPU Usage حدود ۱۵٪ است، اما ThreadPool Queue Length و ThreadPool Thread Count پیوسته افزایش می‌یابند و Request Latency به‌شدت بالا می‌رود. با فرض اینکه زمان پاسخ‌دهی سرویس خارجی ثابت مانده است، کدام گزینه محتمل‌ترین علت این رفتار را بیان می‌کند؟

```csharp
app.MapGet("/orders", async () =>
{
    string json = httpClient
        .GetStringAsync(url)
        .Result;

    await Task.Delay(10);

    return Results.Ok(json);
});
```
1. Task.Delay باعث اشغال ThreadPool Threadها در طول انتظار می‌شود.

2. کندی برنامه ناشی از CPU Saturation هنگام اجرای Continuationها است.

3. استفاده از Result باعث Blocking و احتمال ThreadPool Starvation می‌شود.

4. افزایش Thread Count نشان می‌دهد ThreadPool به‌اندازه کافی ظرفیت آزاد دارد.

- **گزینه صحیح:** **۳**

- **تحلیل عملکرد:** در Endpoint ارائه‌شده، فراخوانی `httpClient.GetStringAsync(url)` یک عملیات Asynchronous را آغاز می‌کند. اما استفاده از خصوصیت Result باعث می‌شود Thread جاری، در صورت تکمیل‌نشدن Task، تا پایان عملیات HTTP مسدود بماند.

در شرایط High Traffic، تعداد زیادی Request ممکن است هم‌زمان وارد این بخش شوند و تعداد قابل‌توجهی از ThreadPool Threadها را درگیر انتظار Blocking کنند.

در نتیجه ممکن است Threadهای کافی برای پردازش Requestهای جدید و اجرای سایر Work Itemها در دسترس نباشند. ThreadPool تلاش می‌کند با اضافه کردن Threadهای جدید این کمبود را جبران کند، اما ممکن است نتواند با سرعت کافی پاسخگوی بار ورودی باشد.

افزایش هم‌زمان ThreadPool Queue Length، ThreadPool Thread Count و Request Latency در کنار CPU Usage پایین، از نشانه‌های مهم احتمال ThreadPool Starvation است.

نسخه مناسب‌تر Endpoint به‌شکل زیر است:

```csharp
app.MapGet("/orders", async () =>
{
    string json = await httpClient
        .GetStringAsync(url);

    await Task.Delay(10);

    return Results.Ok(json);
});
```
در نسخه اصلاح‌شده، هنگام انتظار واقعی برای پاسخ HTTP، نیازی به مسدود نگه داشتن Thread جاری نیست.

- **نکته کلیدی مرور:** CPU Usage پایین الزاماً به معنی وجود ظرفیت کافی برای پردازش Requestها نیست. ممکن است CPU ظرفیت آزاد داشته باشد، اما Threadهای زیادی به دلیل Blocking در دسترس نباشند.

## سؤال 10
در قطعه کد زیر، یک Exception پیش از اولین await در متد `GetValueAsync` رخ می‌دهد. با توجه به نحوه ثبت و انتشار Exception در متدهای async Task، ترتیب صحیح خروجی برنامه چیست؟

```csharp
async Task<int> GetValueAsync(bool fail)
{
    if (fail)
        throw new InvalidOperationException();

    await Task.Delay(100);

    return 42;
}

try
{
    Task<int> task = GetValueAsync(true);

    Console.WriteLine("A");

    Console.WriteLine(task.Status);

    await task;

    Console.WriteLine("B");
}
catch (InvalidOperationException)
{
    Console.WriteLine("C");
}
```
1. `C`

2. `A` سپس `Faulted` سپس `C`

3. `A` سپس `Running` سپس `B` سپس `C`

4. `A` سپس `RanToCompletion` سپس `B`

- **گزینه صحیح:** **۲**

- **تحلیل عملکرد:** در متد `GetValueAsync`، هنگامی که مقدار fail برابر true باشد، یک `InvalidOperationException` پیش از اولین await رخ می‌دهد.

از آنجا که متد با `async Task<int>` تعریف شده است، Exception رخ‌داده در بدنه متد مستقیماً از محل فراخوانی به بلوک catch منتقل نمی‌شود؛ بلکه در Task بازگشتی ثبت می‌شود.

بنابراین فراخوانی متد یک Task با وضعیت Faulted برمی‌گرداند. سپس A چاپ شده و با بررسی `task.Status` مقدار Faulted نمایش داده می‌شود.

هنگامی که برنامه به `await task` می‌رسد، Exception اصلی منتشر شده و اجرای برنامه وارد بلوک catch می‌شود. در نتیجه C چاپ خواهد شد و دستور چاپ B اجرا نمی‌شود.

- **نکته کلیدی مرور:** در یک متد async Task، حتی Exceptionهایی که در بدنه متد پیش از اولین await رخ می‌دهند، در Task بازگشتی ثبت می‌شوند. این رفتار با یک متد معمولی که صرفاً نوع بازگشتی Task دارد، متفاوت است.

## سؤال 11
در قطعه کد زیر، متد `Task.WhenAny` روی دو Task اجرا شده است که یکی ناموفق و دیگری هنوز تکمیل‌نشده است. با توجه به تفاوت میان وضعیت Task بازگشتی از WhenAny و وضعیت Task برنده، خروجی برنامه چیست؟

```csharp
Task<int> failed = Task.FromException<int>(
    new InvalidOperationException("Error"));

var tcs = new TaskCompletionSource<int>();

Task<int> pending = tcs.Task;

Task<Task<int>> race = Task.WhenAny(
    failed, pending);

Task<int> winner = await race;

Console.WriteLine(race.Status);
Console.WriteLine(winner.Status);
```
1. در await race یک InvalidOperationException رخ می‌دهد.

2. `Faulted` سپس `Faulted`

3. `RanToCompletion` سپس `RanToCompletion`

4. `RanToCompletion` سپس `Faulted`

- **گزینه صحیح:** **۴**

- **تحلیل عملکرد:** متد `Task.WhenAny` منتظر می‌ماند تا حداقل یکی از Taskهای ورودی به یک وضعیت نهایی برسد. این وضعیت می‌تواند موفقیت، شکست یا لغو عملیات باشد.

در این مثال Task اول با `Task.FromException` ایجاد شده و از همان ابتدا در وضعیت Faulted قرار دارد. Task دوم هنوز تکمیل نشده است. بنابراین Task اول به‌عنوان Task برنده انتخاب می‌شود.

نوع Task بازگشتی از WhenAny برابر `Task<Task<int>>` است. هنگامی که از `await race` استفاده می‌شود، نتیجه آن خود Task برنده است، نه نتیجه اجرای Task برنده.

از آنجا که WhenAny وظیفه خود را با پیدا کردن اولین Task تکمیل‌شده انجام داده است، وضعیت race برابر `RanToCompletion` خواهد بود؛ حتی اگر Task برنده در وضعیت Faulted باشد.

برای مشاهده Exception اصلی باید Task برنده نیز await شود:

```csharp
Task<int> winner = await race;

int result = await winner;
```
در این صورت، await دوم باعث انتشار `InvalidOperationException` خواهد شد.

- **نکته کلیدی مرور:** موفقیت Task بازگشتی از WhenAny به معنی موفقیت Task برنده نیست. این دو Task وضعیت و Lifecycle مستقلی دارند.

## سؤال 12
دو متد زیر در Endpointهای جداگانه یک ASP.NET Core Application استفاده شده‌اند. با توجه به نحوه انتظار در Thread.Sleep و Task.Delay، کدام تحلیل درباره مصرف Thread در طول زمان انتظار صحیح است؟

```csharp
// Version A
async Task ProcessAAsync()
{
    Thread.Sleep(500);

    await Task.CompletedTask;
}

// Version B
async Task ProcessBAsync()
{
    await Task.Delay(500);
}
```
1. نسخه A هنگام انتظار Thread را Block می‌کند؛ نسخه B می‌تواند آن را آزاد کند.

2. هر دو نسخه Thread را Block می‌کنند؛ زیرا زمان انتظار یکسان است.

3. نسخه B یک Thread اختصاصی برای مدیریت Timer ایجاد می‌کند.

4. وجود async در نسخه A باعث می‌شود Thread.Sleep غیرمسدودکننده باشد.

- **گزینه صحیح:** **۱**

- **تحلیل عملکرد:** در نسخه A، متد `Thread.Sleep(500)` باعث می‌شود Thread جاری به مدت حدود ۵۰۰ میلی‌ثانیه مسدود شود. در این مدت Thread مشغول محاسبات CPU نیست، اما نمی‌تواند برای اجرای سایر عملیات مورد استفاده قرار گیرد.

وجود کلمه کلیدی async در تعریف متد این رفتار را تغییر نمی‌دهد. همچنین `await Task.CompletedTask` باعث تعلیق متد نمی‌شود، زیرا Task موردنظر از قبل تکمیل شده است.

در نسخه B، `Task.Delay(500)` یک انتظار Asynchronous مبتنی بر Timer ایجاد می‌کند. اگر Task مربوط به Delay هنوز تکمیل نشده باشد، await باعث تعلیق متد و بازگشت کنترل به فراخواننده می‌شود.

در این حالت نیازی نیست یک Thread به‌صورت اختصاصی در طول زمان انتظار مسدود بماند. پس از پایان زمان Delay، ادامه متد برای اجرا آماده می‌شود.

این تفاوت در ASP.NET Core اهمیت زیادی دارد، زیرا مسدود شدن تعداد زیادی Thread می‌تواند ظرفیت پردازش Requestهای هم‌زمان را کاهش دهد.

- **نکته کلیدی مرور:** مصرف نکردن CPU با آزاد بودن Thread یکسان نیست. Thread.Sleep باعث Blocking می‌شود، اما Task.Delay امکان انتظار غیرمسدودکننده را فراهم می‌کند.

## سؤال 13
فرض کنید قطعه کد زیر در محیط ASP.NET Core اجرا می‌شود. شناسه Thread پیش و پس از اجرای await ذخیره و با یکدیگر مقایسه شده است. با توجه به رفتار ConfigureAwait(false)، کدام گزینه درباره خروجی برنامه صحیح است؟

```csharp
async Task ExecuteAsync()
{
    int before = Environment.CurrentManagedThreadId;

    await Task.Delay(100)
              .ConfigureAwait(false);

    int after = Environment.CurrentManagedThreadId;

    Console.WriteLine(before == after);
}

await ExecuteAsync();
```
1. همیشه True است؛ زیرا async Thread جدید ایجاد نمی‌کند.

2. همیشه False است؛ زیرا ConfigureAwait(false) Thread را تغییر می‌دهد.

3. ممکن است True یا False باشد؛ ادامه اجرا الزاماً روی Thread قبلی نیست.

4. همیشه False است؛ زیرا Task.Delay روی یک Thread اختصاصی اجرا می‌شود.

- **گزینه صحیح:** **۳**

- **تحلیل عملکرد:** در این مثال، شناسه Thread جاری پیش از اجرای await ذخیره می‌شود. سپس متد با استفاده از `Task.Delay(100)` یک انتظار Asynchronous ایجاد می‌کند.

اگر Task مربوط به Delay هنوز تکمیل نشده باشد، اجرای متد معلق می‌شود. پس از تکمیل Task، ادامه متد برای اجرا آماده خواهد شد.

استفاده از `ConfigureAwait(false)` مشخص می‌کند که برای اجرای Continuation نیازی به تلاش برای بازگشت به SynchronizationContext یا TaskScheduler قبلی نیست. با این حال، این تنظیم تضمین نمی‌کند که ادامه اجرا حتماً روی Thread دیگری انجام شود.

در ASP.NET Core معمولاً SynchronizationContext اختصاصی وجود ندارد. بنابراین Continuation ممکن است روی همان ThreadPool Thread قبلی یا روی یک ThreadPool Thread دیگر اجرا شود.

در نتیجه، مقایسه شناسه Thread پیش و پس از await می‌تواند True یا False باشد و هیچ‌کدام از این نتایج به‌تنهایی نشان‌دهنده رفتار اشتباه برنامه نیست.

- **نکته کلیدی مرور:** ConfigureAwait(false) ابزار تغییر اجباری Thread نیست. همچنین Thread Identity و SynchronizationContext دو مفهوم متفاوت هستند.

## سؤال 14
در قطعه کد زیر، یکی از Taskهای ورودی به `Task.WhenAll` از ابتدا ناموفق است، اما Task دیگر هنوز تکمیل نشده است. با توجه به نحوه تکمیل Task تجمیعی و انتشار Exception، کدام گزینه خروجی برنامه را به‌درستی بیان می‌کند؟

```csharp
Task<int> first = Task.FromException<int>(
    new InvalidOperationException());

var tcs = new TaskCompletionSource<int>(
    TaskCreationOptions.RunContinuationsAsynchronously);

Task<int> second = tcs.Task;

Task<int[]> all = Task.WhenAll(first, second);

Console.WriteLine(all.IsCompleted);

tcs.SetResult(100);

try
{
    await all;
}
catch (InvalidOperationException)
{
    Console.WriteLine(all.Status);
}
```
1. `True` سپس `Faulted`؛ زیرا اولین Task با Exception پایان یافته است.

2. `False` سپس `RanToCompletion`؛ زیرا آخرین Task موفق بوده است.

3. `True` سپس `Canceled`؛ زیرا Exception باعث لغو سایر Taskها می‌شود.

4. `False` سپس `Faulted`؛ زیرا WhenAll منتظر تکمیل تمام Taskها می‌ماند.

- **گزینه صحیح:** **۴**

- **تحلیل عملکرد:** در این مثال، Task اول با `Task.FromException` ایجاد شده و از همان ابتدا در وضعیت Faulted قرار دارد. Task دوم توسط TaskCompletionSource ایجاد شده و هنوز تکمیل نشده است.

متد `Task.WhenAll` یک Task تجمیعی ایجاد می‌کند که تنها زمانی تکمیل خواهد شد که تمام Taskهای ورودی به یکی از وضعیت‌های نهایی رسیده باشند.

بنابراین شکست Task اول باعث نمی‌شود Task تجمیعی بلافاصله تکمیل شود. از آنجا که Task دوم هنوز Pending است، مقدار `all.IsCompleted` برابر False خواهد بود.

پس از اجرای `tcs.SetResult(100)`، Task دوم با موفقیت تکمیل می‌شود. اکنون تمام Taskهای ورودی به وضعیت نهایی رسیده‌اند.

با وجود موفقیت Task دوم، Task تجمیعی به دلیل Exception موجود در Task اول در وضعیت Faulted قرار می‌گیرد. هنگام اجرای `await all`، Exception منتشر شده و برنامه وارد بلوک catch می‌شود. در نتیجه وضعیت Faulted چاپ خواهد شد.

- **نکته کلیدی مرور:** Task.WhenAll به‌صورت پیش‌فرض Fail-Fast نیست. همچنین شکست یک Task باعث لغو خودکار سایر Taskهای ورودی نمی‌شود و موفقیت آخرین Task نمی‌تواند شکست Taskهای قبلی را جبران کند.

## سؤال 15
در یک ASP.NET Core Application، دو Endpoint زیر برای انجام محاسبات سنگین نوشته شده‌اند. فرض کنید تعداد زیادی Request هم‌زمان وارد برنامه می‌شوند و CPU نزدیک به حداکثر ظرفیت خود کار می‌کند. با توجه به ماهیت CPU-bound متد Calculate، کدام تحلیل درباره Endpoint B نسبت به Endpoint A صحیح است؟

```csharp
long Calculate()
{
    long sum = 0;

    for (int i = 0; i < 100_000_000; i++)
    {
        sum += i;
    }

    return sum;
}

// Endpoint A
app.MapGet("/a", () =>
{
    return Results.Ok(Calculate());
});

// Endpoint B
app.MapGet("/b", async () =>
{
    long result = await Task.Run(Calculate);

    return Results.Ok(result);
});
```
1. Task.Run هزینه CPU را کاهش نمی‌دهد و الزاماً Scalability را بهتر نمی‌کند.

2. Endpoint B هنگام اجرای Calculate هیچ ThreadPool Thread را اشغال نمی‌کند.

3. Endpoint B همیشه Throughput بیشتری دارد؛ زیرا Request Thread آزاد می‌شود.

4. Task.Run محاسبات CPU-bound را به عملیات I/O-bound تبدیل می‌کند.

- **گزینه صحیح:** **۱**

- **تحلیل عملکرد:** در Endpoint A، متد Calculate مستقیماً فراخوانی می‌شود و محاسبات روی Thread اجراکننده Request انجام می‌شوند. تا پایان حلقه، این Thread درگیر عملیات CPU-bound خواهد بود.

در Endpoint B، همان محاسبات با استفاده از `Task.Run(Calculate)` روی ThreadPool زمان‌بندی می‌شوند. اگر Task هنگام await هنوز تکمیل نشده باشد، مسیر اولیه Request می‌تواند معلق شود و Thread آن برای پردازش کارهای دیگر در دسترس قرار گیرد.

با این حال، عملیات Calculate همچنان به یک ThreadPool Thread و زمان پردازشی CPU نیاز دارد. بنابراین استفاده از Task.Run باعث حذف هزینه محاسبات یا افزایش ظرفیت واقعی CPU نمی‌شود.

در شرایطی که CPU نزدیک به حداکثر ظرفیت خود قرار دارد، انتقال محاسبات به ThreadPool ظرفیت پردازشی جدیدی ایجاد نمی‌کند. حتی ممکن است زمان‌بندی Taskها و Context Switching هزینه اضافی به برنامه تحمیل کنند.

در UI Application، استفاده از Task.Run برای انتقال محاسبات سنگین به یک Thread دیگر می‌تواند از مسدود شدن UI Thread جلوگیری کرده و Responsiveness را بهبود دهد. اما در ASP.NET Core، Thread اجراکننده Request معمولاً خودش از ThreadPool تأمین شده است؛ بنابراین انتقال محاسبات به ThreadPool لزوماً مزیت مشابهی ایجاد نمی‌کند.

برای بهبود Scalability در محاسبات سنگین باید از راهکارهایی مانند بهینه‌سازی الگوریتم، کنترل Concurrency، محدود کردن حجم کار یا انتقال پردازش به سرویس‌های Background استفاده کرد.

- **نکته کلیدی مرور:** Asynchrony برای بهینه‌سازی انتظار در عملیات I/O-bound بسیار مؤثر است، اما محدودیت ظرفیت CPU در عملیات CPU-bound را برطرف نمی‌کند.
