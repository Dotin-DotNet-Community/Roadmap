# تحلیل و بررسی جامع آزمون تخصصی Entity Framework Core و LINQ
**تاریخ برگزاری: ۶ آبان ۱۴۰۵**

این جزوه تحلیلی شامل صورت سوالات، پاسخ صحیح، تشریح مکانیزم پشت‌صحنه در EF Core و نکته کلیدی مرور برای مصاحبه‌ها و آزمون‌های تخصصی است.

---

### سوال ۱
```csharp
public async Task<List<UserDto>> GetActiveUsersAsync(AppDbContext db)
{
    IEnumerable<User> query = db.Users;

    return query
        .Where(u => u.IsActive)
        .Take(10)
        .Select(u => new UserDto(u.Id, u.FullName))
        .ToList();
}
```
**رفتار این کد در زمان اجرا چگونه خواهد بود؟**
1. کل رکوردهای جدول به RAM منتقل و فیلتر در کلاینت انجام می‌شود.
2. کوئری با شرط WHERE و TOP(10) در دیتابیس اجرا می‌شود.
3. خطای کامپایل می‌دهد چون متد مستقیم ToList روی IEnumerable مجاز نیست.
4. خطای InvalidOperationException در زمان اجرا رخ می‌دهد.

* **گزینه صحیح:** **۱**
* **تحلیل عملکرد:** متغیر `query` به صورت صریح با تایپ `IEnumerable<User>` تعریف شده است؛ در نتیجه کامپایلر به جای اکستنشن متدهای `Queryable` (متصل به Expression Tree)، متدهای کلاسی `Enumerable` (مبتنی بر دلیگیت و LINQ to Objects) را فراخوانی می‌کند. این موضوع باعث می‌شود کل جدول بدون هیچ فیلتری از دیتابیس واکشی و در حافظه کلاینت لود شود و فیلترها در RAM اعمال شوند.
* **نکته کلیدی مرور:** 
  > تغییر تایپ از `IQueryable` به `IEnumerable` مرز واکشی داده (Materialization Boundary) را به کلاینت تغییر می‌دهد. برای ساخت کوئری‌های شرطی پویا همیشه از `IQueryable<T>` یا `var` استفاده کنید.

### سوال ۲
```csharp
public async Task ProcessOrdersAsync(AppDbContext db)
{
    var stream = db.Orders
        .Where(o => o.Status == OrderStatus.Completed)
        .AsEnumerable();

    foreach (var order in stream)
    {
        await SendEmailAsync(order.CustomerEmail);
    }
}
```
**کدام مورد توصیف درستی از رفتار این کد است؟**
1. تمام سفارشات در همان خط اول در حافظه بافر می‌شوند.
2. دیتا استریم می‌شود اما کانکشن تا پایان حلقه باز می‌ماند.
3. کانکشن دیتابیس در هر دور حلقه خودکار باز و بسته می‌شود.
4. به دلیل تداخل همزمانی، خطای زمان اجرا پرتاب می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** متد `AsEnumerable()` برخلاف `ToList()`، داده‌ها را فوراً بافر نمی‌کند، بلکه رکوردها را سطر به سطر استریم (Yield Return) می‌کند. اگر داخل حلقه عملیات غیرهمگام با زمان اجرای بالا (مثل `SendEmailAsync`) رخ دهد، `DataReader` و کانکشن متصل به پایگاه داده برای مدت طولانی باز باقی می‌مانند که می‌تواند باعث اتمام ظرفیت Connection Pool شود.
* **نکته کلیدی مرور:** 
  > در سناریوهایی که درون حلقه، فراخوانی طولانی I/O دارید، داده‌ها را با `ToListAsync` یا دسته‌بندی (Paging/Batching) لود کنید تا کانکشن دیتابیس بلافاصله آزاد شود.

### سوال ۳
```csharp
var result = await db.Customers
    .Include(c => c.Orders)
    .Select(c => new CustomerOrderCountDto
    {
        CustomerName = c.Name,
        TotalOrders = c.Orders.Count()
    })
    .ToListAsync();
```
**عملکرد متد `.Include(c => c.Orders)` در این کوئری چیست؟**
1. ضروری است و بدون آن خطای NullReferenceException می‌دهد.
2. اضافه و بی‌اثر است؛ Projection با Select آن را نادیده می‌گیرد.
3. باعث اضافه شدن یک LEFT JOIN سنگین و دانلود اقلام می‌شود.
4. خطای InvalidOperationException تولید می‌کند.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** هنگامی که از Projection سفارشی (`Select`) استفاده می‌کنید، EF Core ساختار خروجی مورد نظر را بررسی کرده و تنها ستون‌ها و ساب‌کوئری‌های مورد نیاز (در اینجا یک `COUNT`) را در SQL می‌سازد. در این سناریو متد `Include` به طور خودکار نادیده گرفته شده و تاثیری در SQL نهایی ندارد.
* **نکته کلیدی مرور:** 
  > استفاده از `Include` قبل از `Select` معمولاً افزونه بیهوده (Redundant) است؛ موتور کوئری‌ساز EF Core در زمان Projection نیازی به بارگذاری صریح موجودیت‌های رابطه‌ای ندارد.

### سوال ۴
```csharp
public static bool HasValidNationalCode(string code) => code?.Length == 10;

public async Task<List<Member>> GetValidMembersAsync(AppDbContext db)
{
    return await db.Members
        .Where(m => HasValidNationalCode(m.NationalCode))
        .ToListAsync();
}
```
**نتیجه اجرای این کد در EF Core 3.0 به بعد چیست؟**
1. تمام داده‌ها لود و تابع در حافظه کلاینت اجرا می‌شود.
2. با موفقیت به توابع داخلی SQL مثل LEN ترجمه می‌شود.
3. خطای InvalidOperationException رخ می‌دهد؛ ترجمه به SQL ممکن نیست.
4. شرط Where در دیتابیس نادیده گرفته شده و رد می‌شود.

* **گزینه صحیح:** **۳**
* **تحلیل عملکرد:** از زمان EF Core 3.0 قابلیت خاموش و ناخواسته Client Evaluation در بند `Where` حذف شده است. اگر تابعی در شرط `Where` آورده شود که معادل SQL آن برای دیتابیس مشخص نشده باشد، خطای زمان اجرا پرتاب خواهد شد تا از مصرف ناخواسته حافظه و دانلود کل جدول جلوگیری شود.
* **نکته کلیدی مرور:** 
  > توابع C# درون فیلتر `Where` قابل ترجمه مستقیم به SQL نیستند، مگر اینکه مستقیماً با متدهای سازگار با دیتابیس (مانند `m.NationalCode.Length == 10`) بازنویسی شوند یا از طریق User Defined Function (UDF) به دیتابیس نگاشت داده شده باشند.

### سوال ۵
```csharp
// Lazy Loading فعال است
var books = await db.Books.Take(50).ToListAsync();
foreach (var book in books)
{
    Console.WriteLine($"{book.Title} - Reviews: {book.Reviews.Count}");
}
```
**مجموعاً چند کوئری به دیتابیس ارسال خواهد شد؟**
1. ۱ کوئری شامل JOIN بین کتاب‌ها و نظرات.
2. ۲ کوئری؛ یک کوئری کتاب و یک کوئری با شرط IN برای نظرات.
3. ۵۱ کوئری (۱ کوئری برای کتاب‌ها + ۵۰ کوئری برای نظرات).
4. ۵۰ کوئری؛ کتاب اول کوئری نمی‌زند.

* **گزینه صحیح:** **۳**
* **تحلیل عملکرد:** این سناریو مصداق بارز خطای معماری N+1 است. کوئری اول ۵۰ کتاب را لود می‌کند و در ادامه به ازای هر بار خواندن Navigation Property روی `book.Reviews`، یک کوئری مجزا به دیتابیس ارسال می‌شود (۱ + ۵۰ = ۵۱).
* **نکته کلیدی مرور:** 
  > Lazy Loading می‌تواند به راحتی گلوگاه کارایی (Performance Bottleneck) ایجاد کند. استفاده از Eager Loading (`Include`) یا انجام Projection مناسب در زمان کوئری‌زدن بهترین راه‌حل پیشگیری از N+1 است.

### سوال ۶
**چه زمانی Explicit Loading (`Entry().Collection().LoadAsync()`) ارجح است؟**
1. وقتی همیشه به تمام زیرمجموعه‌ها در ۱۰۰٪ موارد نیاز داریم.
2. وقتی لود فرزندان تنها بر اساس شروط تجاری خاص و گاهی نیاز باشد.
3. وقتی می‌خواهیم حتماً کوئری با INNER JOIN سریع تولید شود.
4. وقتی روی کوئری از AsNoTracking استفاده کرده باشیم.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** بارگذاری صریح یا Explicit Loading زمانی بهترین انتخاب است که والد از قبل در حافظه موجود است و فقط در برخی شاخه‌های شرطی منطق تجاری (Business Logic) تصمیم می‌گیریم فرزندان را از دیتابیس واکشی کنیم.
* **نکته کلیدی مرور:** 
  > Eager Loading (`Include`) همیشه تمام فرزندان را می‌آورد، اما Explicit Loading اجازه می‌دهد بارگذاری فرزندان به تاخیر بیفتد و تنها در صورت برقراری شرایط خاص، کوئری زده شود.

### سوال ۷
```csharp
var query = db.Products.AsQueryable();
if (filterByCategory)
    query = query.Where(p => p.CategoryId == 5);

var final = query.Take(10);
var count = await query.CountAsync();
var list = await final.ToListAsync();
```
**تعامل این کد با دیتابیس چگونه است؟**
1. ۱ کوئری واحد برای شمارش و دریافت همزمان زده می‌شود.
2. ۲ کوئری مجزا به دیتابیس زده می‌شود (یکی Count و یکی List).
3. شرط Take(10) روی متد Count هم اعمال می‌شود.
4. خطای همزمانی برای اجرای دو کوئری متوالی رخ می‌دهد.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** به دلیل ماهیت اجرای تاخیری (Deferred Execution)، تا زمانی که متد ترمینال فراخوانی نشود کوئری زده نمی‌شود. در این کد متدهای `CountAsync` و `ToListAsync` دو عملگر مجزا هستند؛ کوئری اول `SELECT COUNT(...)` بدون `TOP` را اجرا می‌کند و کوئری دوم لیست ۱۰تایی را برمی‌گرداند.
* **نکته کلیدی مرور:** 
  > تعریف `IQueryable` ارزان است و دیتابیس را درگیر نمی‌کند، اما فراخوانی هر عملگر پایانی (Terminal Operator) مانند `CountAsync`، `ToListAsync` یا `AnyAsync` یک کوئری مستقل و مجزا به سرور می‌فرستد.

### سوال ۸
```csharp
public static string FormatLog(string name, decimal price) => $"{name}: {price}";

var list = await db.Products
    .Where(p => p.IsAvailable)
    .Select(p => new {
        p.Id,
        Display = FormatLog(p.Name, p.Price)
    })
    .ToListAsync();
```
**نحوه اجرای متد `FormatLog` چگونه است؟**
1. متد با توابع داخلی SQL در سرور ترجمه و اجرا می‌شود.
2. خطای ترجمه می‌دهد چون متد C# در کوئری مجاز نیست.
3. فیلدها از دیتابیس خوانده شده و متد در کلاینت (RAM) اجرا می‌شود.
4. کل جدول بدون فیلتر Where واکشی می‌شود.

* **گزینه صحیح:** **۳**
* **تحلیل عملکرد:** برخلاف بند `Where`، استفاده از متدهای C# در بالاترین سطح `Select` (معروف به Top-Level Projection) مجاز است. EF Core ستون‌های لازم (`Id`، `Name`، `Price`) را با اعمال فیلتر از دیتابیس می‌خواند و سپس متد `FormatLog` را هنگام نگاشت شیء در حافظه کلاینت صدا می‌زند.
* **نکته کلیدی مرور:** 
  > فیلتر کردن باید سمت سرور ترجمه شود (SQL Translation)، اما تبدیل ساختار و قالب‌بندی نهایی داده‌ها در آخرین `Select` می‌تواند بدون ایجاد خطا سمت کلاینت (Client-Side Evaluation) انجام گیرد.

### سوال ۹
```csharp
var article = await db.Articles
    .AsNoTracking()
    .Include(a => a.Comments)
    .FirstOrDefaultAsync(a => a.Id == id);

article.ViewsCount++;
await db.SaveChangesAsync();
```
**نتیجه اجرای این کد چیست؟**
1. تغییر با موفقیت در دیتابیس UPDATE می‌شود.
2. هیچ آپدیتی رخ نمی‌دهد چون انتیتی Track نمی‌شود.
3. خطای زمان اجرا به خاطر ترکیب AsNoTracking و Include رخ می‌دهد.
4. دیتابیس به دلیل عدم بستن تراکنش قفل می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** متد `AsNoTracking()` به Change Tracker اطلاع می‌دهد که وضعیت موجودیت را پیگیری نکند؛ در نتیجه آبجکت با حالت `Detached` در حافظه قرار دارد. تغییرات روی پراپرتی‌های چنین آبجکتی توسط `DbContext` ردیابی نشده و دستور `SaveChanges` هیچ کوئری `UPDATE` تولید نخواهد کرد.
* **نکته کلیدی مرور:** 
  > برای سناریوهای فقط-خواندنی (Read-Only) حتماً از `AsNoTracking` برای کاهش بار حافظه استفاده کنید، اما اگر قرار است موجودیت ویرایش و ذخیره شود، نباید حالت Tracking آن غیرفعال گردد.

### سوال ۱۰
```csharp
var orders = await db.Orders
    .Include(o => o.Items.Where(i => i.UnitPrice > 1000))
    .ToListAsync();
```
**رفتار این کوئری (Filtered Include) چیست؟**
1. فقط سفارشاتی را می‌آورد که آیتم بالای ۱۰۰۰ دارند.
2. تمام سفارشات را می‌آورد اما آیتم‌های زیر ۱۰۰۰ آن‌ها لود نمی‌شوند.
3. خطای کامپایل می‌دهد؛ شرط Where داخل Include مجاز نیست.
4. شرط نادیده گرفته شده و تمام آیتم‌ها کامل لود می‌شوند.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** قابلیت Filtered Include که از EF Core 5.0 اضافه شد، شرط فیلتر را صرفاً روی واکشی موجودیت‌های وابسته (فرزندان) اعمال می‌کند نه والد. یعنی همه سفارش‌ها لود می‌شوند، اما لیست `Items` هر سفارش فقط حاوی اقلام با قیمت بالای ۱۰۰۰ خواهد بود.
* **نکته کلیدی مرور:** 
  > اگر می‌خواهید خود سفارش‌ها (والد) فیلتر شوند، باید شرط را در `Where` اصلی بنویسید (`db.Orders.Where(o => o.Items.Any(...))`). شرط داخل `Include` تاثیری بر فیلتر شدن خود والد ندارد.

### سوال ۱۱
```csharp
var blog = await db.Blogs
    .Include(b => b.Posts)
    .Include(b => b.Contributors)
    .FirstOrDefaultAsync(b => b.Id == 1);
```
**اگر یک وبلاگ ۵۰ پست و ۲۰ مشارکت‌کننده داشته باشد، خروجی خام SQL چند سطر است؟**
1. ۷۰ سطر داده بازگردانده می‌شود.
2. ۱۰۰۰ سطر داده برمی‌گردد (ضرب دکارتی ۵۰ در ۲۰).
3. فقط ۱ سطر بازگردانده می‌شود.
4. ۵۱ سطر داده برمی‌گردد.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** در صورتی که روی یک موجودیت چندین مجموعه هم‌سطح (Sibling Collections) با استفاده از `Include` واکشی شوند، در حالت پیش‌فرضِ Single Query یک ضرب دکارتی رخ می‌دهد ($50 \times 20 = 1000$ سطر خروجی خام پایگاه داده با حجم زیادی داده تکراری).
* **نکته کلیدی مرور:** 
  > برای جلوگیری از انفجار کارتنزی (Cartesian Explosion) هنگام لود چند کالکشن وابسته، از متد `.AsSplitQuery()` استفاده کنید تا برای هر کالکشن کوئری‌های مجزا به پایگاه داده ارسال شود.

### سوال ۱۲
```csharp
var minPrice = 100;
var query = db.Products.Where(p => p.Price >= minPrice);

minPrice = 500;

var result = await query.ToListAsync();
```
**حداقل قیمت در کوئری نهایی SQL چقدر خواهد بود؟**
1. مقدار ۱۰۰ (ارزیابی در لحظه تعریف شرط).
2. مقدار ۵۰۰ (ارزیابی متغیر در لحظه اجرای کوئری).
3. خطای کامپایل به دلیل تغییر متغیر بعد از تعریف کوئری.
4. شرط نادیده گرفته شده و بدون قیمت فیلتر می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** متغیرهای محلی در Expression Tree به شکل Closure نگهداری می‌شوند. با توجه به ویژگی اجرای تاخیری (Deferred Execution)، ارزیابی مقدار متغیر نه در زمان ساخت کوئری، بلکه در لحظه اجرای آن (`ToListAsync`) انجام می‌شود؛ بنابراین مقدار ۵۰۰ به عنوان پارامتر ارسال می‌گردد.
* **نکته کلیدی مرور:** 
  > ارزیابی پارامترهای بیرونی در کوئری‌های LINQ در زمان اجرا (Execution Time) انجام می‌شود، نه در زمان پیکربندی و ساخت اولیه کوئری (Definition Time).

### سوال ۱۳
```csharp
var a = await db.Users.FindAsync(userId);
var b = await db.Users.FirstOrDefaultAsync(u => u.Id == userId);
```
**تفاوت رفتار این دو متد چیست؟**
1. تفاوتی ندارند و هر دو مستقیم به دیتابیس کوئری می‌زنند.
2. متد Find ابتدا Change Tracker را چک می‌کند، ولی متد دوم همیشه به سرور می‌رود.
3. متد FirstOrDefaultAsync از رم می‌خواند ولی Find به سرور می‌رود.
4. هر دو متد حتماً داده را فقط از کش محلی می‌خوانند.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** متد `FindAsync` روی کلید اصلی (Primary Key) کار می‌کند و قبل از ارسال کوئری به دیتابیس، کش سطح اولِ `DbContext` (Local Change Tracker) را بررسی می‌کند؛ اگر موجودیت قبلاً لود شده باشد بدون کوئری دیتابیس بازگردانده می‌شود. اما `FirstOrDefaultAsync` یک `IQueryable` است و همیشه به دیتابیس ارسال می‌شود.
* **نکته کلیدی مرور:** 
  > برای دریافت موجودیت بر اساس کلید اصلی (PK)، متد `FindAsync` به دلیل استفاده از کش داخلی عملکرد بسیار بهینه‌تری نسبت به `FirstOrDefaultAsync` دارد.

### سوال ۱۴
```csharp
try {
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex) {
    // دریافت مقادیر ثبت‌شده در دیتابیس
}
```
**کدام گزینه مقدار فعلی موجود در پایگاه داده را برمی‌گرداند؟**
1. `ex.Entries.Single().GetDatabaseValuesAsync()`
2. `ex.Entries.Single().OriginalValues`
3. `ex.Entries.Single().CurrentValues`
4. `db.Accounts.FromSqlRaw(...)`

* **گزینه صحیح:** **۱**
* **تحلیل عملکرد:** در زمان بروز تداخل همزمانی (Concurrency Conflict):
  * `CurrentValues`: مقادیر فعلی در حافظه برنامه است که قصد ذخیره آن را داشتیم.
  * `OriginalValues`: مقادیری است که قبلاً در ابتدای دریافت از دیتابیس واکشی شده بود.
  * `GetDatabaseValuesAsync()`: با یک کوئری مستقیم مقادیر تازه‌ثبت‌شده توسط کاربر/تراکنش رقیب را از دیتابیس می‌خواند.
* **نکته کلیدی مرور:** 
  > برای حل تداخل در Optimistic Concurrency، با استفاده از متد `GetDatabaseValuesAsync()` وضعیت جدید دیتابیس را خوانده و با مقادیر جاری مقایسه یا جایگزین می‌کنیم.

### سوال ۱۵
```csharp
// الف
var exists1 = await db.Orders.Where(o => !o.IsPaid).CountAsync() > 0;
// ب
var exists2 = await db.Orders.AnyAsync(o => !o.IsPaid);
```
**کدام مقایسه از نظر کارایی در دیتابیس درست است؟**
1. روش الف سریع‌تر است چون شمارش ایندکس‌ها بهینه‌تر است.
2. هر دو به دستور یکسان SELECT COUNT ترجمه می‌شوند.
3. روش ب سریع‌تر است چون با دستور EXISTS به محض اولین نتیجه متوقف می‌شود.
4. روش ب به دلیل لود داده در حافظه کلاینت کندتر است.

* **گزینه صحیح:** **۳**
* **تحلیل عملکرد:** متد `CountAsync() > 0` موتور دیتابیس را وادار به شمارش تمامی رکوردهای منطبق بر شرط در کل جدول/ایندکس می‌کند (`SELECT COUNT(...)`). در مقابل، `AnyAsync` به دستور بهینه `IF EXISTS` یا `CASE WHEN EXISTS` تبدیل شده و به محض مشاهده اولین رکورد، اسکن دیتابیس را متوقف می‌کند.
* **نکته کلیدی مرور:** 
  > برای بررسی وجود یا عدم وجود داده، هرگز از `Count() > 0` استفاده نکنید؛ همیشه از متد `AnyAsync()` برای دستیابی به بالاترین کارایی استفاده شود.
