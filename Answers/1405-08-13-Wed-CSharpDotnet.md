# تحلیل و بررسی جامع آزمون مبانی معماری C# 11 و .NET 7
**تاریخ برگزاری: ۱۳ آبان ۱۴۰۵**  
**منبع مرجع:** کتاب *C# 11 and .NET 7 – Modern Cross-Platform Development Fundamentals* (سطح کاردان)

---

### سوال ۱ (C# vs .NET Architecture)
**کدام گزاره رابطه بین کامپایلر C# (Roslyn) و .NET Runtime (CLR) را دقیق‌تر توصیف می‌کند؟**
1. کامپایلر مستقیماً سورس‌کد را به زبان ماشین پلتفرم هدف (Native Code) تبدیل می‌کند.
2. کامپایلر کد IL تولید می‌کند؛ اما وظیفه JIT و مدیریت حافظه بر عهده CLR است.
3. کامپایلر فقط وظیفه بررسی سینتکس را دارد و کدنویسی مستقیماً توسط CLR اجرا می‌شود.
4. مدیریت منابع مدیریت‌نشده (Unmanaged) در زمان کامپایل توسط Roslyn انجام می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** زبان C# یک زبان کامپایلری دومرحله‌ای است. کامپایلر Roslyn (چه از طریق `csc` و چه `dotnet build`) سورس‌کد C# را اعتبارسنجی کرده و به یک زبان میانی مستقل از سخت‌افزار به نام **IL** (Intermediate Language / CIL) همراه با متادیتا درون یک فایل اسمبلی (`.dll` یا `.exe`) تبدیل می‌کند. در زمان اجرا، **CLR** با فعال‌سازی کامپایلر درجا (JIT) این بایت‌کد را به دستورات Native ماشین ترجمه و حافظه را مدیریت می‌کند.
* **نکته کلیدی مرور:**
  > تفکیک وظایف: **Roslyn** مسئول تبدیل `C# -> IL` در زمان ساخت (Build-Time) است، در حالی که **CLR** مسئول تبدیل `IL -> Native Machine Code` در زمان اجرا (Run-Time) است.

### سوال ۲ (.NET Evolution)
**کدام ویژگی معماری در «.NET مدرن» (از .NET 5 به بعد) نسبت به «.NET Framework» تغییر کرد؟**
1. حذف کامل وابستگی به Common Intermediate Language (CIL).
2. یکپارچه‌سازی پلتفرم‌ها در یک ران‌تایم واحد Cross-Platform بدون نیاز به Mono.
3. بازگشت معماری مدیریت حافظه به سبک C++ بدون نیاز به Garbage Collector.
4. حذف کامل مفهوم Assembly و DLL در بیلد نهایی پروژه‌ها.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** قبل از .NET 5، اکوسیستم دات‌نت چندپاره بود: .NET Framework مخصوص ویندوز، .NET Core برای سرورهای چندسکویی، و Mono/Xamarin برای موبایل. از نسخه .NET 5 به بعد (معروف به Modern .NET)، یک ران‌تایم واحد، کتابخانه کلاس پایه یکسان (BCL) و زنجیره ابزار CLI یکپارچه برای تمام پلتفرم‌ها معرفی شد.
* **نکته کلیدی مرور:**
  > نام‌گذاری بدون پسوند (مثل .NET 6، .NET 7 و...) نشان‌دهنده چشم‌انداز *One .NET* است؛ دیگر پسوندهایی مانند "Core" یا "Framework" در نسخه‌های مدرن استفاده نمی‌شوند.

### سوال ۳ (SDK vs Runtime در ترمینال)
فرض کنید روی سرور تنها پکیج ران‌تایم نصب شده و خروجی زیر نمایش داده می‌شود:
```bash
$ dotnet --list-runtimes
Microsoft.NETCore.App 7.0.10 [/usr/share/dotnet/shared/Microsoft.NETCore.App]

$ dotnet build MyProject.csproj
```
**نتیجه اجرای دستور `dotnet build` روی این سیستم چیست؟**
1. پروژه با موفقیت کامپایل شده و در پوشه bin قرار می‌گیرد.
2. با خطای نبود .NET SDK مواجه می‌شود؛ چون Runtime امکان بیلد ندارد.
3. پروژه بیلد می‌شود اما خروجی آن به جای dll به صورت exe خواهد بود.
4. خطای ناسازگاری نسخه ران‌تایم با سیستم‌عامل پرتاب می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** پکیج **.NET Runtime** فقط شامل پیش‌نیازهای اجرای برنامه‌های از پیش کامپایل‌شده است (CLR، BCL و دستور `dotnet exec/run app.dll`). برای کامپایل، تست و پکیج‌بندی، وجود کامپایلر Roslyn، موتور MSBuild و ابزارهای توسعه ضروری است که همگی فقط در پکیج **.NET SDK** عرضه می‌شوند.
* **نکته کلیدی مرور:**
  > سرورهای پروداکشن معمولاً برای حفظ امنیت و سبکی، فقط نیاز به **Runtime** دارند، در حالی که ماشین توسعه‌دهنده یا سرورهای CI/CD حتماً به **SDK** نیاز دارند.

### سوال ۴ (CLR Internals)
**کدام مورد جزو وظایف مستقیم Common Language Runtime (CLR) «نیست»؟**
1. تبدیل بایت‌کد IL به کدهای ماشین از طریق JIT Compilation.
2. اعمال قوانین Type Safety و مدیریت استثناها (Exception Handling).
3. مدیریت چرخه عمر اشیا و آزادسازی حافظه با Garbage Collector.
4. تبدیل سورس‌کد متنی C# به کدهای Intermediate Language (IL).

* **گزینه صحیح:** **۴**
* **تحلیل عملکرد:** تبدیل کد متنی به IL کاری مربوط به زبان برنامه‌نویسی خاص (مثل C# یا F#) است و توسط کامپایلر مربوطه (مانند Roslyn) انجام می‌گیرد. ران‌تایم (CLR) اصلاً سورس متنی C# را نمی‌بیند؛ ورودی CLR، بایت‌کدهای استاندارد IL است.
* **نکته کلیدی مرور:**
  > سه مسئولیت حیاتی CLR در زمان اجرا عبارتند از: **JIT Compilation**، **Memory Management (GC)**، و **Security/Type Enforcement**.

### سوال ۵ (dotnet CLI Mechanism)
**دستور `dotnet run` دقیقاً چه سازوکاری را در پس‌زمینه اجرا می‌کند؟**
1. صرفاً یک میانبر برای اجرای فایل اسمبلی خروجی بدون هیچ چک اضافه‌ای است.
2. در صورت وجود تغییر، ابتدا build را اجرا و سپس باینری خروجی را اجرا می‌کند.
3. کل فرایند را مستقیماً در رم اجرا کرده و فایلی روی دیسک ذخیره نمی‌کند.
4. سورس‌کد را مستقیماً و بدون کامپایل، به‌صورت اسکریپتی تفسیر و اجرا می‌کند.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** دستور `dotnet run` طراحی شده تا تجربه توسعه روزمره سریع باشد. این دستور ابتدا یک کامپایل افزایشی (Incremental Build) انجام می‌دهد؛ یعنی اگر سورس دست‌نخورده باشد فوراً اسمبلی قبلی را اجرا می‌کند و در غیر این صورت، ابتدا پروژه را کامپایل کرده و سپس خروجی اجرایی را فراخوانی می‌کند.
* **نکته کلیدی مرور:**
  > اگر مطمئن هستید کد تغییری نکرده و می‌خواهید سرعت اجرای دستور را بالا ببرید، می‌توانید از فلگ `--no-build` در دستور `dotnet run` استفاده کنید.

### سوال ۶ (Execution Pipeline & JIT)
**مزیت اصلی کامپایل JIT در زمان اجرا نسبت به کامپایل مستقیم به ماشین (Native) چیست؟**
1. اجرای اولیه بسیار سریع‌تر کدها در مقایسه با باینری‌های کامپایل‌شده.
2. عدم نیاز به نصب هرگونه فایل پیش‌نیاز روی سیستم‌عامل مقصد.
3. قابلیت بهینه‌سازی کدهای ماشین با توجه به معماری دقیق CPU در سیستم میزبان.
4. حذف کامل مراحل کامپایل و پردازش سریع‌تر سورس‌کد در زمان استقرار.

* **گزینه صحیح:** **۳**
* **تحلیل عملکرد:** کامپایل AOT یا کامپایل پیش از اجرا مجبور است کدهای باینری را برای پایین‌ترین سطح مشترک یک معماری (مانند حداقل‌های x64) کامپایل کند تا همه‌جا کار کند. اما کامپایلر JIT چون دقیقاً روی سخت‌افزار میزبان اجرا می‌شود، ویژگی‌های خاص پردازنده مثل دستورات برداری (AVX-512 یا SSE4) را تشخیص داده و کد ماشین را اختصاصاً برای آن CPU اپتیمایز می‌کند.
* **نکته کلیدی مرور:**
  > عیب JIT «زمان استارت‌آپ اولیه (Cold Start)» است؛ اما مزیت بارز آن «تولید کدهای بهینه‌سازی‌شده برای ویژگی‌های دقیق سخت‌افزار در زمان اجرا» است.

### سوال ۷ (نقش .sln در مقایسه با .csproj)
```xml
<!-- WebApp.csproj -->
<Project Sdk="Microsoft.NET.Sdk.Web">
  <PropertyGroup>
    <TargetFramework>net7.0</TargetFramework>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="..\Core\Core.csproj" />
  </ItemGroup>
</Project>
```
**اگر فایل Solution (.sln) حذف شود، اجرای `dotnet build WebApp.csproj` چه نتیجه‌ای دارد؟**
1. با خطا متوقف می‌شود؛ بیلد وابستگی‌ها به وجود فایل Solution وابسته است.
2. پروژه WebApp و وابستگی Core با موفقیت کامپایل می‌شوند.
3. فقط پروژه جاری بیلد شده و رفرنس‌های ProjectReference نادیده گرفته می‌شوند.
4. خطای MSBuild رخ می‌دهد چون متادیتای وابستگی فقط در sln ذخیره می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** فایل `.sln` صرفاً یک محفظه ساختاری برای IDEها (مانند Visual Studio) جهت مدیریت گروه‌بندی پروژه‌ها و پیکربندی‌های کلی است. هسته اصلی ساخت کد در اکوسیستم دات‌نت، فایل‌های `.csproj` و موتور MSBuild هستند. MSBuild تگ `<ProjectReference>` را تحلیل کرده و ابتدا پروژه والد و پروژه‌های وابسته به آن را طبق درخت وابستگی بیلد می‌کند.
* **نکته کلیدی مرور:**
  > پروژه‌های مدرن دات‌نت بدون نیاز به وجود فایل Solution به طور کامل با CLI قابل کامپایل و تست هستند.

### سوال ۸ (Target Framework Moniker)
```xml
<!-- CommonLib.csproj -->
<PropertyGroup>
  <TargetFramework>net7.0</TargetFramework>
</PropertyGroup>

<!-- ClientApp.csproj -->
<PropertyGroup>
  <TargetFramework>netcoreapp3.1</TargetFramework>
</PropertyGroup>
<ItemGroup>
  <ProjectReference Include="..\CommonLib\CommonLib.csproj" />
</ItemGroup>
```
**نتیجه کامپایل پروژه `ClientApp` چه خواهد بود؟**
1. با موفقیت بیلد شده و کدهای net7 به صورت خودکار دانگرید می‌شوند.
2. خطای کامپایل رخ می‌دهد؛ فریم‌ورک پایین‌تر نمی‌تواند به نسخه بالاتر ارجاع دهد.
3. بدون خطا کامپایل می‌شود ولی در زمان اجرا خطای MissingMethod می‌دهد.
4. پروژه بیلد می‌شود ولی خروجی ClientApp به فریم‌ورک net7 ارتقا می‌یابد.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** قاعده حاکم بر TFM (Target Framework Moniker) جریان سازگاری رو به بالا است؛ یعنی یک پروژه با فریم‌ورک بالاتر (`net7.0`) می‌تواند کتابخانه‌های فریم‌ورک پایین‌تر (`netcoreapp3.1` یا `netstandard2.0`) را رفرنس دهد، اما عکس آن غیرممکن است زیرا فریم‌ورک قدیمی‌تر توانایی تضمین وجود APIها و ران‌تایم فریم‌ورک جدیدتر را ندارد.
* **نکته کلیدی مرور:**
  > اگر کتابخانه‌ای دارید که باید همزمان در چند فریم‌ورک مختلف استفاده شود، باید از Multi-targeting استفاده کنید:  
  `<TargetFrameworks>netcoreapp3.1;net7.0</TargetFrameworks>`

### سوال ۹ (Build vs Publish)
```bash
$ dotnet build --configuration Release
$ ls bin/Release/net7.0/
App.dll   App.pdb   Newtonsoft.Json.dll   appsettings.json
```
**اگر فایل کانفیگ زیر در csproj باشد، چرا در خروجی build بالا قرار نگرفته است؟**
```xml
<Content Include="secrets.json">
  <CopyToPublishDirectory>Always</CopyToPublishDirectory>
</Content>
```
1. به دلیل خطای نحوی، این تگ در زمان پردازش نادیده گرفته شده است.
2. این تنظیم فقط زمان dotnet publish اثر دارد، نه زمان dotnet build.
3. فایل‌های json حتماً باید به عنوان None تعریف شوند تا در بیلد بیایند.
4. این فایل به صورت مخفی درون باینری App.dll کامپایل و تزریق شده است.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** در MSBuild دو ویژگی مجزا برای کپی فایل‌ها وجود دارد:
  * `CopyToOutputDirectory`: فایل را در زمان `dotnet build` به پوشه خروجی (`bin/...`) منتقل می‌کند.
  * `CopyToPublishDirectory`: فایل را منحصراً هنگام فراخوانی دستور `dotnet publish` به پوشه استقرار منتقل می‌کند.
* **نکته کلیدی مرور:**
  > تفکیک این دو تگ برای سناریوهایی است که فایلی فقط برای سرور پروداکشن یا بسته نهایی استقرار لازم است و نباید خروجی محیط توسعه را شلوغ کند.

### سوال ۱۰ (Top-level Statements)
```csharp
// Program.cs
Console.WriteLine("Initializing...");
return 0;

void PrintLog() => Console.WriteLine("Done.");
```
**کامپایلر C# این ساختار را در خروجی IL چگونه پیاده‌سازی می‌کند؟**
1. یک متد استاتیک Entry Point درون کلاسی در فضای‌نام گلوبال تولید می‌کند.
2. سورس را به صورت اسکریپتی بدون ایجاد متد نقطه ورود اجرا می‌کند.
3. خطای کامپایل می‌دهد؛ متد محلی درون فایل روت مجاز نیست.
4. دستور return عدد، به دلیل نبود امضای int Main باعث خطای کامپایل می‌شود.

* **گزینه صحیح:** **۱**
* **تحلیل عملکرد:** قابلیت Top-level Statements یک قند سینتکسی (Syntactic Sugar) است. ساختار داخلی CLR تغییری نکرده است؛ Roslyn در زمان بیلد کلاسی مخفی تحت عنوان `<Program>$` و متد استاتیکی تحت عنوان `<Main>$(string[] args)` تولید می‌کند و کدهای شما را درون آن قرار می‌دهد. اگر کد خروجی بازگرداند، متد با امضای `int` وگرنه با امضای `void` ساخته می‌شود.
* **نکته کلیدی مرور:**
  > در یک پروژه فقط و فقط یک فایل می‌تواند از ساختار Top-level Statements استفاده کند زیرا پروژه نمی‌تواند بیش از یک متد ورودی (Entry Point) داشته باشد.

### سوال ۱۱ (Deployment Models: SCD vs FDD)
دستور زیر برای انتشار یک سرویس اجرا شده است:
```bash
dotnet publish -c Release -r linux-x64 --self-contained false
```
**اجرای این خروجی روی سیستم‌عامل لینوکس مقصد به چه چیزی وابسته است؟**
1. نصب بودن .NET SDK نسخه ۷ برای ترجمه کدهای برنامه در مقصد.
2. نصب بودن .NET Runtime متناظر با معماری x64 روی سیستم‌عامل سرور.
3. نیازی به هیچ پیش‌نیازی ندارد چون معماری هدف لینوکس صراحتاً قید شده است.
4. نصب بودن شبیه‌ساز کتابخانه‌های ویندوز برای فراخوانی توابع پایه.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** روش انتشار به صورت `Framework-dependent Deployment (FDD)` (که با آرگومان `--self-contained false` مشخص می‌شود) ران‌تایم و کتابخانه‌های پایه را در پکیج قرار نمی‌دهد تا حجم استقرار کم بماند؛ بنابراین روی سرور مقصد باید از قبل ران‌تایم دات‌نت متناسب با پلتفرم نصب شده باشد.
* **نکته کلیدی مرور:**
  > آرگومان `-r linux-x64` فقط باینری اجرایی را برای معماری هدف آداپته می‌کند، اما وضعیت استقرار وابستگی‌های ران‌تایم را پرچم `--self-contained` تعیین می‌کند.

---

### سوال ۱۲ (مزیت استقرار Self-Contained)
**استفاده از روش Self-Contained Deployment (SCD) چه برتری کلیدی در استقرار دارد؟**
1. حجم فایل خروجی نسبت به حالت Framework-dependent بسیار کمتر است.
2. نیازی به نصب بودن هیچ نسخه‌ای از .NET Runtime روی ماشین مقصد ندارد.
3. سرعت کامپایل برنامه در محیط مبدا را به طرز چشمگیری افزایش می‌دهد.
4. آپدیت‌های امنیتی ران‌تایم را خودکار از سیستم‌عامل دریافت می‌کند.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** در حالت Self-Contained Deployment، موتور CLR و کلیه اسمبلی‌های مورد نیاز BCL همراه فایل باینری برنامه درون پوشه خروجی قرار می‌گیرند. در نتیجه، این پکیج حتی روی ماشینی که دات‌نت اصلاً روی آن نصب نیست، بدون هیچ پیش‌نیازی اجرا می‌شود.
* **نکته کلیدی مرور:**
  > بهای استقلال در روش SCD، افزایش چشمگیر حجم بسته استقرار (چند ده مگابایت بیشتر) و مسئولیت دستی در به‌روزرسانی پچ‌های امنیتی ران‌تایم است.

### سوال ۱۳ (Cross-Platform Execution)
```csharp
using Microsoft.Win32;

var key = Registry.CurrentUser.OpenSubKey(@"Software\MyApp");
Console.WriteLine(key?.ValueCount);
```
**اجرای این قطعه کد روی سیستم‌عامل لینوکس چه نتیجه‌ای خواهد داشت؟**
1. داده‌های رجیستری در یک فایل ساختاریافته در پوشه etc لینوکس خوانده می‌شوند.
2. خطای زمان اجرای PlatformNotSupportedException رخ می‌دهد.
3. خطای کامپایل رخ می‌دهد؛ فضای‌نام مایکروسافت در لینوکس وجود ندارد.
4. بدون خطا اجرا شده و متغیر key همیشه برابر null خواهد بود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** اگرچه .NET مدرن چندسکویی است، اما برخی کلاس‌ها به سیستم‌عامل خاصی گره خورده‌اند (Platform-Specific APIs). رجیستری یک مفهوم منحصراً ویندوزی است و پکیج سازگاری ویندوز این API را در زمان کامپایل معتبر می‌داند، اما در زمان اجرا روی سیستم‌عامل لینوکس یا مک، خطای `PlatformNotSupportedException` پرتاب می‌کند.
* **نکته کلیدی مرور:**
  > برای کدهای وابسته به پلتفرم، از شرط‌های زمان اجرا استفاده کنید:  
  `if (OperatingSystem.IsWindows()) { ... }`

### سوال ۱۴ (Memory Leaks & GC)
```csharp
public class EventHub
{
    public static event Action OnTick;
}

public class MetricsCollector
{
    public MetricsCollector() => EventHub.OnTick += HandleTick;
    private void HandleTick() { /* ... */ }
}
```
**چرا ساخت مکرر نمونه‌های `MetricsCollector` و رها کردن آن‌ها باعث نشت حافظه می‌شود؟**
1. رویداد استاتیک ارجاع شیء را زنده نگه داشته و مانع آزادسازی توسط GC می‌شود.
2. متد هندلر پرایوت باعث قفل شدن شیء در نسل شماره صفر رم می‌شود.
3. حافظه اشیایی با نام متد تکراری توسط Garbage Collector پایش نمی‌شود.
4. رویداد OnTick کل نخ‌های پردازشی برنامه را به وضعیت بلاک می‌برد.

* **گزینه صحیح:** **۱**
* **تحلیل عملکرد:** هر Event در C# یک ارجاع قوی (Strong Reference) از طریق دلیگیت به نمونه شیء هدف (`Target`) نگه می‌دارد. از آنجا که `EventHub` و رویداد آن استاتیک هستند، تا پایان عمر اپلیکیشن در حافظه باقی می‌مانند (یک شیء ریشه یا GC Root هستند). به همین دلیل، نمونه‌های `MetricsCollector` از نگاه Garbage Collector همچنان قابل دسترسی (Reachable) تلقی شده و هرگز پاکسازی نمی‌شوند.
* **نکته کلیدی مرور:**
  > ثبت‌نام در رویدادهای با طول عمر بالاتر (به‌ویژه رویدادهای استاتیک) از عوامل اصلی نشت حافظه در دات‌نت است. همیشه در متد `Dispose` لغو اشتراک (`-=`) انجام دهید.

### سوال ۱۵ (SDK Pinning via global.json)
```json
{
  "sdk": {
    "version": "7.0.200",
    "rollForward": "disable"
  }
}
```
**اگر روی سیستمی فقط SDK نسخه `7.0.300` نصب باشد، اجرای `dotnet build` چه نتیجه‌ای دارد؟**
1. بیلد با موفقیت از نسخه جدیدتر 7.0.300 استفاده می‌کند و صرفاً اخطار می‌دهد.
2. با خطا متوقف می‌شود؛ نسخه منطبق با فایل تنظیمات در سیستم پیدا نشده است.
3. بیلد موفقیت‌آمیز است چون rollForward به طور خودکار نادیده گرفته می‌شود.
4. نسخه 7.0.200 به صورت خودکار از مخازن رسمی مایکروسافت دانلود می‌شود.

* **گزینه صحیح:** **۲**
* **تحلیل عملکرد:** فایل `global.json` برای قفل کردن نسخه SDK در پروژه‌های تیمی و خطوط لوله CI/CD به کار می‌رود. وقتی ویژگی `rollForward` روی مقدار `disable` تنظیم شود، CLI دات‌نت از هرگونه جهش به نسخه‌های پچ یا فیچر بالاتر جلوگیری کرده و دقیقاً خواستار نسخه قیدشده است؛ در صورت نبود آن، بیلد فوراً متوقف می‌شود.
* **نکته کلیدی مرور:**
  > مقدار پیش‌فرض `rollForward` معمولاً `latestPatch` است (اجازه پیشروی به پچ‌های بالاتر)، اما در سناریوهای پین دقیق نسخه، تنظیم `disable` مانع تغییر ناخواسته رفتار کامپایلر می‌شود.
